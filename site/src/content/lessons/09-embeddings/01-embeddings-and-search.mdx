Every model in this course so far has produced an answer: a type, a title, a breed. This module is about a model that produces no answer at all, and is one of the most widely deployed kinds there is.

## What an embedding model does

An <mark>embedding model</mark> reads a text and returns a list of numbers, called an <mark>embedding</mark> or a vector. The numbers mean nothing one at a time. What matters is distance: the model is trained so that texts with similar meaning get lists that are close together, and unrelated texts get lists that are far apart.

That one property is enough to build search. Embed every document once and store the results. When a question comes in, embed it the same way and return the stored documents whose embeddings are nearest. This is how most "search by meaning" works, and it is the retrieval step behind systems that look things up before answering.

Closeness is usually measured by <mark>cosine similarity</mark>: how nearly two lists point in the same direction, from 1 for identical direction down through 0 for unrelated.

## Where the money goes

A search system built on embeddings pays in three places.

- **Embedding the documents.** Once per document, and again whenever you change models.
- **Storing the embeddings.** Every document's list of numbers has to be kept, and for fast search mostly kept in memory.
- **Embedding each query.** On every search, before anything else can happen. This sets a floor on how fast search can feel.

The length of the list is set by the model. Larger models tend to produce longer lists, so a bigger embedding model costs more three times over: slower to run on documents, slower to run on each query, and more to store.

## Why distill one

>
  All three. The smaller model runs faster on documents and on queries, and its shorter lists take less than half the space. That is unusual: most optimizations help one cost and leave the others alone. The price is search quality, and the rest of this module is about measuring how much is lost and recovering as much as possible.
</PredictReveal>

There is a catch that the earlier modules did not have. Embeddings from two different models are not comparable. If you change the model, every stored document has to be embedded again with the new one. A distilled embedding model is a replacement for the whole index, not a drop-in swap for one request.

## The task for this module

The data is the banking messages again. The job is search: given a new customer message, find earlier messages about the same thing. A support team might use that to pull up how similar requests were handled.

- **The collection** is the pool of about 9,000 messages.
- **The queries** are 1,000 test messages.
- **The teacher** is an embedding model with 335 million weights that produces 1,024 numbers per text.
- **The student** has 33 million weights and produces 384.

No labels are used for training in this module at all. The messages' types are used only afterwards, to score the results.
