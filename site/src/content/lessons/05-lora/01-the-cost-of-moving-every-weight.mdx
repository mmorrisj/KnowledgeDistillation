So far the student has been a small encoder with about 150 million weights. Every one of them moved during training, and it fitted on the GPU with room to spare. This module moves to students that generate text, with ten to fifty times as many weights. At that size, moving every weight stops being free.

## Training needs more memory than running

To run a model, the GPU holds one copy of its weights. To train it, the GPU holds a good deal more for every weight:

- the weight itself;
- its gradient, the direction it should move;
- two running averages the optimizer keeps for each weight.

In full precision that comes to about 16 bytes per weight, against 2 bytes to run the model in the 16-bit format the labs use.

## A second cost: a full copy per task

Full fine-tuning produces a complete new set of weights. A 1.5 billion weight model is about 3 GB on disk. If you fine-tune it for five tasks, you store and serve five 3 GB models.

## What LoRA changes

<mark>LoRA</mark> freezes every original weight and trains a small set of new ones attached to the model. Frozen weights need no gradient and no optimizer state, so memory during training falls to roughly what it takes to run the model. The result of training is a small file, called an <mark>adapter</mark>, usually a few megabytes to a few tens of megabytes. Five tasks means one base model and five small adapters.

## What LoRA does not change

Recall the mix-up from lesson 1.4: LoRA does not make the model you run any smaller or faster. After training, the model is the same size as before, plus the adapter. LoRA is a way to afford training a bigger student. Making the model smaller is the job of distillation, which is why the two are used together: distillation decides what the student learns from, and LoRA decides which of its weights move.

In this module's lab you will do both at once. The training labels come from the teacher, and the student is trained with LoRA. That is the "teacher-written labels with LoRA" cell of the map from lesson 1.3.
